# rotorch (Rotor Torch)

`rotorch` supplies popular [Geometric Algebra](https://bivector.net/) (GA) based equivariant machine learning architectures
like [`cgenn`](https://github.com/DavidRuhe/clifford-group-equivariant-neural-networks) ([Ruhe et al., 2023](https://arxiv.org/abs/2305.11141)) and [`GATr`](https://github.com/Qualcomm-AI-research/geometric-algebra-transformer) ([Brehmer et al., 2023](https://arxiv.org/abs/2305.18415)), but optimized beyond the reference implementations by leveraging [`kingdon`](https://github.com/tBuLi/kingdon)'s 
optimal compilation of GA expressions. 
Group Equivariant neural networks ([Cohen and Welling, 2016](https://arxiv.org/abs/1602.07576)) rose to prominence as an answer to the question: what if my data is rotated/translated compared to the training data.
Instead of augmenting the training data with transformed versions of the training data, the neural network architecture should just be invariant to such transformations.
GA takes this to the next level because all of its operators are geometrically meaningful and equivariant, making it the natural framework to express these ideas and offering clear advantages ([Ruhe et al., 2023](https://arxiv.org/abs/2305.11141); [Brehmer et al., 2023](https://arxiv.org/abs/2305.18415)) over traditional implementations that used irreps of groups ([Thomas et al., 2018](https://arxiv.org/abs/1802.08219); [Geiger and Smidt, 2022](https://arxiv.org/abs/2207.09453)).

What rotorch offers:
- Geometric primitives for points, lines, planes, rotations, translations etc. that live on the GPU by leveraging [torch](https://pytorch.org). 
- The binary (and most unary) operators of GA are equivariant by definition. As long as you build modules using these operations, equivariance is guaranteed.
- The modules of popular GA based architectures have been translated into `rotorch`. (Currently CGENN and GATr, with [`cliffordlayers`](https://github.com/microsoft/cliffordlayers) ([Brandstetter et al., 2023](https://arxiv.org/abs/2209.04934)) to follow.)
- Uniform archetectures for different algebra's: no need for your modules to be "algebra aware" like in the reference implementations mentioned above.
- GA operations at the core of the modules are highly optimized using `kingdon`, which uses symbolic optimization and [Common Subexpression Elimination](https://en.wikipedia.org/wiki/Common_subexpression_elimination) (CSE) to arrive at optimal code to perform the geometric operation at hand. A [`torch.compile`](https://docs.pytorch.org/docs/stable/generated/torch.compile.html) or [`triton`](https://github.com/triton-lang/triton) version of the same thing can never reach anywhere close to this level of optimization on the algebraic level.
- Apply `torch.compile` to optimize the code generated by `kingdon` for a particular device to get the best possible performance.
- Fully backwards compatible with existing torch modules, and indeed torch as a whole. Mind you, these are not always equivariant, so use them with care.

The result of all this is the fastest code on the market to build GA based equivariant neural networks.
Improvements will continue to be made to push this even further.
The [benchmarks](https://tbuli.github.io/rotorch/benchmark.html) put `rotorch` next to the reference implementations on the examples of their own papers.

As an example of how to create models with `rotorch`, consider the  
`cgenn` example to find the convex hull of a point-cloud in 5D.
We construct the pointcloud as vectors in 5D using `kingdon`,
and feed them directly through `torch` and `rotorch` modules.

```py
import torch
from torch import nn
from kingdon import Algebra, MultiVector
from rotorch.nn.cgenn import GeometricProduct, MVLinear


class ConvexHullCGMLP(nn.Module):
    """Regress the volume of a convex hull from the multivectors of its points."""

    def __init__(self, in_features=16, hidden_features=32, out_features=1, num_layers=4,
                 normalization_init=0):
        super().__init__()

        self.net = nn.Sequential(
            MVLinear(in_features, hidden_features, gradewise=False),
            *(GeometricProduct(hidden_features, normalization_init=normalization_init)
              for _ in range(num_layers)),
        )
        self.mlp = nn.Sequential(
            nn.Linear(hidden_features, hidden_features),
            nn.SiLU(),
            nn.Linear(hidden_features, out_features),
        )

    def forward(self, input: MultiVector) -> MultiVector:
        input_normsq = self.net(input).normsq().grade(0)
        return self.mlp(input_normsq.sqrt())

alg = Algebra(5, backend='torch')
points = torch.rand(5, 8, 16)
x = alg.vector(points)     # Vector[(8, 16)]

model = ConvexHullCGMLP()
y = model(x)               # Scalar[(8, 1)]
```

A big advantage of `rotorch` is that the models can be formulated without reference to a specific algebra,
since the algebra comes from the multivectors. (`x` in the example above.)

## Roadmap
- [x] Full compatibility with existing torch modules. This is something the competition does *not* have, because they represent multivectors with shape `(..., channels_in, blades)` where blades is $2^n$. In `kingdon` v3 however, a multivector has shape `(..., channels_in)` and the blade dimension is invisible. (Under the hood the underlying datastructure is `(blades, ..., channels_in)` where moreover blades does not have to be the full algebra, which is where we will get our speed-up from.) The torch modules expect the channels to be the last dimension, which kingdon has!
  - [ ] Full compatibility can be achieved by defining `__torch_function__` on kingdon MultiVectors, at which point the typechecker of torch should accept multivectors directly in its forward function :). I have to decide if that will be part of kingdon, or of this package specifically so as not to polute the kingdon namespace with torch specific stuff.
  - [ ] Symbolic backwards improving over autograd
- [ ] Implement equivariant modules, which the torch ones are generally not.
  - [x] CGENN
  - [x] GATr
  - [ ] cliffordlayers
- [ ] At this stage we have all the infrastructure, and can focus on speeding things up further by implementing further optimizations
  - [x] `torch.compile` as a first improvement.
  - [ ] triton specific printers for `kingdon` that automatically generate triton kernels
- [ ] Benchmark against 
   - [ ] reference implementations
   - [ ] other equivariant implentations like [e3nn](https://github.com/e3nn/e3nn)
